# Development Insight — 技術設計の背景と意思決定

TrendInsight AIの実装における技術的判断とその根拠を解説します。

## 1. なぜ3値分析（Positive / Neutral / Negative）か

### 課題

初期実装で採用した2値分類（positive/negative）では、ニュース見出しの大半が「ネガティブ寄り」に判定される問題が発生しました。

```
高市首相が帰国の途 - nippon.com → positive: 7.9%（実際は中立）
オーストラリア訪問（２） - 首相官邸 → positive: 10.4%（実際は中立）
```

原因は明確で、感情分析モデルが「感情を含まない事実報道」を処理できず、確信度の低いnegative判定を返していたためです。

### 解決

`koheiduck/bert-japanese-finetuned-sentiment` は実際には3クラス（POSITIVE / NEUTRAL / NEGATIVE）を出力するモデルでした。NEUTRAL出力を正しくハンドリングすることで、事実報道は50:50（中立）として扱われるようになりました。

```python
if label == "POSITIVE":
    pos_score = score
elif label == "NEGATIVE":
    neg_score = score
else:  # NEUTRAL
    pos_score = 0.5
    neg_score = 0.5
```

### 補正ロジック

モデルが中立と判定しても、「戦争」「死亡」「倒産」等の強ネガティブ語が含まれる場合はスコアを補正します。これにより「悲惨な経験をした二人のきょうだい…」のような文が誤ってポジティブ判定されることを防止しています。

```python
NEGATIVE_BOOST_WORDS = {"戦争", "悲惨", "孤児", "死亡", ...}  # 34語
boost = sum(1 for w in NEGATIVE_BOOST_WORDS if w in title)
if boost > 0:
    adjustment = min(boost * 0.3, 0.5)
    neg_score = min(neg_score + adjustment, 1.0)
```

## 2. データの多角性 — 3ソースの設計意図

### 情報の非対称性

同じトピックでも、情報源によって論調は大きく異なります。

| ソース | 特性 | 例（「生成AI規制」） |
|--------|------|---------------------|
| Googleニュース | 事実報道中心、中立寄り | 「政府がAI規制法案を提出」 |
| BlueSky | 個人の感情・期待・不安 | 「規制されたら仕事なくなる…」 |
| はてなブックマーク | 批判的分析、論点の指摘 | 「この法案の問題点は○○」 |

この3層構造により、「メディアは肯定的に報じているが、世論は懸念している」といったギャップを定量的に検出できます。

### はてなブックマーク選定の理由

当初はReddit APIを検討しましたが、2023年以降の料金改定により個人開発での利用ハードルが高くなりました。はてなブックマークは：

- **認証不要**（APIキー不要で即座に利用可能）
- **日本語ネイティブ**（英語圏バイアスなし）
- **批判的視点が集まりやすい**（ニュースの裏側を指摘するコメント文化）

という特性があり、「第三者のツッコミ」としての役割に最適です。

### GoogleニュースURL問題の解決

GoogleニュースRSSが返すURLは `https://news.google.com/rss/articles/CBMi...` というラッパーURLで、JavaScriptリダイレクトを使用しているため、`requests`では実際の記事URLに到達できません。

はてなブックマークは実際の記事URLで登録されるため、直接マッチングは不可能でした。解決策として、はてなブックマーク検索RSS（`/search/text?q=keyword&mode=rss`）でキーワード直接検索する方式を採用しています。

## 3. ローカルLLMの選定と推論設計

### モデル選定

| 候補 | サイズ | 日本語品質 | 判定 |
|------|--------|-----------|------|
| gemma-2b-it (Q4) | ~1.5GB | △ 読めるが浅い | 不採用 |
| **ELYZA-JP-8B (Q4_K_M)** | **~4.5GB** | **◎ 実用的** | **採用** |
| Llama-3-70B | ~40GB | ◎ | RAM不足で不可 |

12GB RAM + 4GB swap環境で、BERT感情分析モデル（~500MB）と共存可能な最大サイズとしてELYZA 8B Q4_K_Mを選定しました。

### 量子化の選択

Q4_K_M（4bit量子化、Mixed precision）は品質と速度のバランスが最も良い量子化方式です。Q2やQ3では日本語の流暢さが著しく低下し、Q5以上ではRAM消費が許容範囲を超えます。

### プロンプト設計

LLMに渡すプロンプトは構造化データとして整形し、出力の方向性を明確に指示しています：

```
■ メディア（Googleニュース30件）
  感情: ポジティブ20% / 中立70% / ネガティブ10%
  頻出語: 首相, 訪問, 経済, 連携, 会談
■ はてなブックマーク（第三者コメント）
  感情: ポジティブ10% / 中立30% / ネガティブ60%
  頻出語: 批判, 疑問, 対応, 問題, 指摘

上記データに基づき、以下の観点で3〜5行の総評レポートを作成:
- メディア報道と世論の間に温度差やギャップがあるか
- 各ソースで注目されているポイントの違い
- このトピックに対する世の中の空気感の総合的な読み解き
```

単なる「要約して」ではなく、**ギャップ分析**に焦点を当てた指示を与えることで、LLMの出力品質を担保しています。

### メモリ管理

```python
@st.cache_resource
def load_llm() -> Llama:
    ...
```

`@st.cache_resource`により、モデルはアプリケーションのライフサイクル全体で1回だけロードされます。Streamlitのリラン（ボタン押下等）のたびにモデルを再ロードすることはありません。

## 4. 著作権・プライバシーへの配慮

### APIコストゼロの設計

| ソース | 方式 | コスト |
|--------|------|--------|
| Googleニュース | RSS（公開フィード） | 無料 |
| BlueSky | AT Protocol（公開API） | 無料 |
| はてなブックマーク | 公開JSON API | 無料 |
| 感情分析 | ローカルBERT推論 | 無料 |
| 総評生成 | ローカルLLM推論 | 無料 |

有料APIへの依存をゼロにすることで、個人開発者が継続的に運用可能な設計としています。

### 出典の明記

- はてなブックマークのコメント表示時には「出典: はてなブックマーク」を明記
- 各記事・投稿にはオリジナルURLへのリンクを必ず付与
- BlueSky投稿には著者ハンドルを表示

### サーバー負荷への配慮

はてなブックマークAPIへのアクセスは：
- ブックマーク数上位5件のみに限定
- リクエスト間に0.5秒のスリープを挿入
- フレーズ検索で不要なリクエストを削減

### データの局所性

すべての分析データはローカルの`data/`ディレクトリに保存され、外部サーバーへの送信は一切行いません。ユーザーのプライバシーと分析対象のデータ主権を保護しています。
